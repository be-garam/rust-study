## Rust: 
- 2015년에 ver 1.0을 릴리즈한 새로운 프로그래밍 언어
    - [Rust blog: Announcing Rust 1.0](https://blog.rust-lang.org/2015/05/15/Rust-1.0/)
- 정적 컴파일 언어 (like C++)
    - Q. 정적 컴파일 언어가 뭐지? 이전에 이야기하던 바이너리를 만들어내는 언어? 
        - `<CLAUDE check>` 맞는 이해: 실행하기 전에 소스 코드 전체를 기계어(CPU가 직접 읽는 명령)로 미리 번역해 바이너리 파일을 만들어 두는 언어
        - `<CLAUDE check>` "정적" = "실행 전에(컴파일 시점에) 결정"이라는 뜻, 반대말 "동적" = "실행 중에 결정"
        - `<CLAUDE check>` 타입 검사도 실행 전에 끝남(정적 타입): 타입이 안 맞으면 바이너리 자체가 만들어지지 않음
        - `<CLAUDE check>` Python과의 차이: Python은 실행할 때 인터프리터가 소스를 읽어가며 처리, 타입 오류도 그 줄이 실행되는 순간에야 발견
    - 별도의 런타임을 필요로 하지 않고 가비지 컬렉션도 없음
        - Q. 런타임이 없다는건 os에서 프로그램을 실행시키는 시간인가? GC는 어떻게 없을 수 있지? 
            - `<CLAUDE check>` 런타임의 두 가지 뜻 중 다른 쪽: 여기서는 "실행 시간"이 아니라 "런타임 시스템"
                - 실행 시간(run time): 프로그램이 돌아가는 시점, 컴파일 시점의 반대말
                - 런타임 시스템(runtime): 내 프로그램이 돌아가려면 옆에서 함께 돌아야 하는 보조 프로그램 (예: Python 인터프리터, Java의 JVM)
            - `<CLAUDE check>` "별도의 런타임이 필요 없다" = 바이너리 하나만 있으면 실행 가능, Python처럼 상대 컴퓨터에 인터프리터를 설치할 필요 없음
                - 정확히는 `main` 시작 전 준비 작업 같은 아주 작은 런타임 코드가 바이너리 안에 포함됨, 인터프리터·가상 머신 같은 큰 런타임이 없다는 의미
            - `<CLAUDE check>` GC(가비지 컬렉션): 더 이상 쓰지 않는 메모리를 실행 중에 찾아서 자동으로 반납해 주는 런타임의 기능, Python이 이 방식
            - `<CLAUDE check>` Rust에 GC가 없어도 되는 이유: 메모리를 언제 반납할지를 컴파일러가 실행 전에 결정
                - 1. 모든 값에 주인(owner) 변수가 하나씩 정해짐
                - 2. 컴파일러가 주인 변수의 사용 범위(scope)가 끝나는 지점을 파악
                - 3. 그 지점에 메모리 반납 코드를 자동으로 삽입
                - 4. 실행 중에는 삽입된 코드가 그냥 실행될 뿐, 쓰레기를 찾아다니는 작업 없음
            - `<CLAUDE check>` 이 규칙이 소유권(ownership), Fundamentals 3일차 메모리 관리 단원에서 자세히 다룰 예정
- rustc: LLVM을 백엔드로 사용
    - Q. LLVM이 뭐지? 뭔가 웹개발에서의 백엔드랑은 개념이 다른거 같은데 
        - `<CLAUDE check>` 맞는 이해: 웹의 백엔드(서버)와는 다른 개념, "사용자와 맞닿지 않는 뒤쪽 절반"이라는 비유만 같음
        - `<CLAUDE check>` 컴파일러의 두 부분
            - 프론트엔드: 소스 코드를 읽고 문법·타입 등을 검사한 뒤 중간 표현(IR, 언어와 CPU 어느 쪽에도 묶이지 않은 중간 단계 코드)으로 변환
            - 백엔드: 중간 표현을 최적화하고 특정 CPU용 기계어로 변환
        - `<CLAUDE check>` LLVM: 이 백엔드 역할을 해 주는 오픈소스 컴파일러 도구 모음, C/C++(clang)·Swift 등도 함께 사용
        - `<CLAUDE check>` 컴파일 순서: Rust 소스 → (`rustc` 프론트엔드) → LLVM IR → (LLVM) → 최적화된 기계어 바이너리
        - `<CLAUDE check>` 장점: LLVM이 이미 지원하는 CPU 종류(x86, ARM 등)와 최적화 기술을 Rust가 그대로 활용 → 아래 "다양한 플랫폼과 아키텍쳐 지원"의 근거
- 다양한 플랫폼과 아키텍쳐를 지원하며 다양한 장치에서 사용될 수 있음 = C++가 사용되는 대부분의 곳에서 아용이 가능함
    - 높은 유연성과 제어, 마이크로컨트롤러 같은 제한된 장치로 스케일 다운이 가능
        - Q. 마이크로 컨트롤러가 뭐지? 뭔가 esp32라면 해당 부분에 들어간 칩? 이런걸 의미하는건가? 
            - `<CLAUDE check>` 맞는 이해: ESP32 칩이 바로 마이크로컨트롤러의 한 종류
                - 개발 보드 = 칩 + USB 단자·전원 회로 등 주변 부품, 마이크로컨트롤러는 그중 칩 자체
            - `<CLAUDE check>` 마이크로컨트롤러(MCU): CPU, 메모리(RAM), 저장 공간(플래시), 입출력 핀을 칩 하나에 모두 넣은 아주 작은 컴퓨터
                - 사용처: 세탁기, 리모컨, 센서, 키보드 같은 기기의 제어
            - `<CLAUDE check>` "제한된 장치"의 의미: RAM이 수 KB~수백 KB 수준(노트북은 수 GB, 대략 만 배 이상 차이), 운영체제 없이 프로그램 하나만 실행하는 경우가 많음
            - `<CLAUDE check>` 위 내용과의 연결: 런타임과 GC가 없어서 바이너리가 작고 운영체제 없이도 실행 가능 → 이런 작은 칩까지 스케일 다운 가능

## 토론: 마이크로컨트롤러에서 Rust가 돌아가는 방식
- Q. esp32 같은 마이크로컨트롤러에서는 무거운 python interpreter 대신 LLVM만 돌아가면 되니까 부하가 작은 건가? LLVM을 돌릴 수 있는 칩이라는 기준은 뭐지?
    - `<CLAUDE check>` 틀린 이해: LLVM은 칩 위에서 돌지 않음, 컴파일러의 일부라서 번역 작업을 하는 개발용 컴퓨터에서만 실행
    - `<CLAUDE check>` 실행까지의 순서
        - 1. 개발용 컴퓨터에서 `rustc`(+LLVM)가 Rust 소스를 칩의 CPU가 읽는 기계어로 번역
        - 2. 결과물인 바이너리를 USB로 칩의 저장 공간(플래시)에 옮김
        - 3. 칩에 전원이 들어오면 CPU가 그 기계어를 처음부터 하나씩 읽어 실행
        - 3번 시점의 칩 안에는 `rustc`도 LLVM도 없고 내 프로그램의 기계어만 존재
    - `<CLAUDE check>` 크로스 컴파일(cross-compile): 컴파일하는 컴퓨터와 실행하는 컴퓨터가 다른 방식
    - `<CLAUDE check>` "LLVM을 돌릴 수 있는 칩"이라는 기준은 없음, 올바른 기준은 "LLVM이 그 칩의 CPU용 기계어를 만들어 낼 줄 아는가"
    - `<CLAUDE check>` Python과의 차이
        - Python: 번역을 실행 중에 하므로 인터프리터가 칩 안에 함께 들어가 계속 돌아야 함, 인터프리터만 수 MB라 RAM이 수 KB~수백 KB인 칩에는 넣기 어려움
        - Rust: 번역이 끝난 기계어만 칩에 들어가고 실행 중에는 기계어 실행뿐
        - "무거운 인터프리터가 필요 없어서 부하가 작다"는 맞는 방향, 그 자리를 LLVM이 대신하는 것이 아니라 아무것도 대신하지 않음
- Q. 아니면 메모리쪽 사용량이나 계획이 미리 정해져서 그런가?
    - `<CLAUDE check>` 부분적으로 맞는 이해
        - 맞는 부분: 메모리를 언제 반납할지가 컴파일할 때 정해져서 실행 중에 GC가 돌 필요 없음, GC 코드와 GC가 쓰는 여유 메모리가 통째로 빠짐
        - 정확하지 않은 부분: 메모리를 얼마나 쓸지까지 전부 미리 정해지는 것은 아님, Rust 프로그램도 실행 중에 메모리를 더 요청할 수 있음 (스택/힙을 배울 때 다룰 내용)
- Q. rustc/LLVM은 vsc의 platformIO가 깔려있는 mac, window, ubuntu 같은 데에서 돌아간다고 이해하면 되나? 만들어서 칩에 옮기는 작업을 하는 게 arduino interpreter나 extension인 거고?
    - `<CLAUDE check>` 맞는 이해: `rustc`/LLVM은 개발용 컴퓨터에서 실행, 칩에 옮기는 일은 PlatformIO 같은 도구가 담당
    - `<CLAUDE check>` 고칠 용어: "Arduino 인터프리터"는 없음, Arduino 코드는 C++이고 Rust처럼 미리 컴파일되는 언어
    - `<CLAUDE check>` PlatformIO·Arduino IDE의 역할: 직접 번역하지 않고 다른 프로그램을 순서대로 불러 주는 관리자
        - 1. 컴파일러를 불러 소스를 칩용 바이너리로 번역
        - 2. 업로드 도구를 불러 바이너리를 USB로 칩의 플래시에 기록
    - `<CLAUDE check>` Rust에서는 `cargo`가 관리자 역할: `cargo`가 `rustc`를 불러 컴파일, 칩에 쓰는 일은 별도의 업로드 도구가 담당
- Q. esp32의 CPU는 전자두뇌 정도로 이해하고 있었는데, 해당 CPU의 규칙으로 바꾸는 작업이라는 개념도 들어가는 건가?
    - `<CLAUDE check>` 맞는 이해: CPU는 정해진 목록의 명령만 알아듣고, 그 목록이 CPU 계열마다 다름
    - `<CLAUDE check>` 아키텍처(architecture): 이 명령 목록의 종류
        - x86-64: Intel/AMD 노트북, 데스크톱
        - ARM: 스마트폰, Apple Silicon Mac, 많은 마이크로컨트롤러
        - Xtensa, RISC-V: ESP32 계열
    - `<CLAUDE check>` 같은 "두 수를 더해라"도 아키텍처마다 다른 숫자 조합으로 표기 → 노트북용 바이너리를 ESP32에 넣으면 실행 불가
- Q. rustc로 만들어둔 파일이 binary로 전환되는 과정은 LLVM이 하는데, 칩의 특성에 따라 작성되는 binary는 다를 수 있다는 정도로 이해해도 되나?
    - `<CLAUDE check>` 맞는 이해, 다만 "다를 수 있다"가 아니라 아키텍처가 다르면 반드시 다름
    - `<CLAUDE check>` LLVM은 `rustc` 안에 포함: 따로 실행하지 않고 명령 한 번에 소스에서 바이너리까지 진행
    - `<CLAUDE check>` 중간 결과물(IR)은 그 과정 안에서 넘겨지는 것이라 보통 파일로 보이지 않음
    - `<CLAUDE check>` 타깃(target): 어떤 칩용으로 만들지 컴파일할 때 지정하는 값, 같은 소스라도 타깃을 바꾸면 다른 바이너리 생성


## Benefit

컴파일 시간 메모리 안정: 메모리 버그의 전체 클래스가 컴파일 시간에 방지
- 초기화되지 않는 변수가 없음
    - Q. 초기화된다는거는 메모리에 올라갔다가 해지된다는 걸 의미하는건가? 해지? 초기화가 구체적으로 뭐지
        - `<CLAUDE check>` 틀린 이해: 초기화와 해제는 서로 다른 단계
            - 초기화(initialization): 변수에 처음으로 값을 넣어 주는 일
            - 해제(free): 다 쓴 메모리를 반납하는 일
        - `<CLAUDE check>` 초기화되지 않은 변수: 메모리에 자리는 잡았지만 아직 값을 넣지 않은 변수
            - C에서는 이 상태로 읽으면 그 자리에 남아 있던 쓰레기 값이 읽힘
            - Rust는 값을 넣기 전에 읽는 코드를 컴파일 단계에서 거부
        - `<CLAUDE check>` Python과 비교: 값을 대입해야 변수가 생기므로 같은 문제가 거의 없음 (대입 전에 쓰면 `NameError`)
- 메모리 이중 해제가 원천적으로 불가능
    - `<CLAUDE check>` 이중 해제(double free): 이미 반납한 메모리를 한 번 더 반납하는 버그
- 메모리 해제 후 사용이 원천적으로 불가능
    - `<CLAUDE check>` 해제 후 사용(use after free): 반납한 메모리를 계속 읽거나 쓰는 버그, 그 자리는 이미 다른 용도로 쓰이고 있을 수 있음
- null pointer가 없음
    - Q. 이게 어떻게 가능한거지? null? nan? empty라는 개념이 없다는걸 의미하는건가?
        - `<CLAUDE check>` 포인터(pointer): 메모리의 위치(주소)를 담고 있는 값
        - `<CLAUDE check>` null 포인터: "아무 곳도 가리키지 않음"을 뜻하는 특수한 포인터 값, 모르고 따라가면 프로그램이 죽음
            - Python에서 가장 비슷한 것: `None`, `None`인 줄 모르고 `.속성`을 쓰면 `AttributeError`
            - NaN은 다른 개념: 계산 결과를 숫자로 정할 수 없을 때 나오는 실수(float) 값
        - `<CLAUDE check>` "없음"이라는 개념이 사라진 것은 아님: 값이 없을 수 있는 경우를 `Option`이라는 별도 타입으로 표시
            - 컴파일러가 "없는 경우"를 처리했는지 검사 → 깜빡하고 따라가는 실수 차단
- 뮤텍스를 잠그고 여는 것을 잊어버리는 실수를 할 수 없음
    - Q. 뮤텍스가 뭐지?
        - `<CLAUDE check>` 뮤텍스(mutex, mutual exclusion = 상호 배제): 여러 스레드가 같은 데이터를 동시에 건드리지 못하게 하는 자물쇠 (스레드는 아래 항목 참고)
            - 1. 데이터를 쓰려는 스레드가 자물쇠를 잠금
            - 2. 잠겨 있는 동안 다른 스레드는 대기
            - 3. 다 쓰면 자물쇠를 열어 다음 스레드에게 넘김
        - `<CLAUDE check>` 흔한 실수 두 가지: 잠그지 않고 데이터 사용, 다 쓰고 여는 것을 잊음(다른 스레드가 영원히 대기)
        - `<CLAUDE check>` Rust의 방식: 데이터가 자물쇠 안에 들어 있어 잠가야만 접근 가능, 사용 범위가 끝나면 자동으로 열림
- 스레드간 데이터 레이스를 막아줌
    - Q. 이게 무슨말이지? 스레드의 구체적인 의미는? 뭔가 내가 julia를 경험할때 멀티코어 cpu에게 여러 일을 시켰을 때, gc가 전역적으로 돌면서 엄청느려졌던 경험이 있는데 이거랑 관련된건가? 다른건가? 
        - `<CLAUDE check>` 스레드(thread): 한 프로그램 안에서 동시에 진행되는 실행 흐름, 멀티코어 CPU에서는 코어마다 다른 스레드를 실제로 동시에 실행
        - `<CLAUDE check>` 데이터 레이스(data race): 둘 이상의 스레드가 같은 데이터를 동시에 건드리고, 그중 하나 이상이 값을 바꾸는데, 순서 조율이 없는 상황
            - 결과가 실행할 때마다 달라지는 버그의 원인
        - `<CLAUDE check>` Julia 경험과의 관계: 멀티스레딩이라는 주제는 같지만 다른 현상
            - Julia에서 겪은 것: GC가 돌 때 모든 스레드를 멈춰서 느려지는 성능 문제
            - 데이터 레이스: 속도가 아니라 결과가 틀려지는 정확성 문제
            - 그 경험은 오히려 위의 "GC 없음 → 예측 가능한 성능"과 연결되는 사례
- 반복자가 갑자기 무효화되는 경우가 없음
    - Q. 반복자라는건 for, while 문을 말하는 건가? 
        - `<CLAUDE check>` 가깝지만 다른 이해: `for` 문 자체가 아니라 `for` 문이 내부에서 쓰는 "다음 원소를 하나씩 꺼내 주는 객체", `while`과는 무관
            - Python의 `iter(리스트)`가 돌려주는 것과 같은 개념
        - `<CLAUDE check>` 반복자 무효화: 순회하는 도중에 그 컬렉션을 수정해서 반복자가 가리키던 위치가 어긋나는 것
            - Python 예: `for` 도중 리스트에서 원소를 지우면 일부를 건너뜀, dict는 `RuntimeError`
        - `<CLAUDE check>` Rust는 순회 중인 컬렉션을 수정하는 코드를 컴파일 단계에서 거부

정의되지 않은 런타임 동작 없음: Rust 문이 실행하는 작업은 지정되지 않은 상태로 두지 않음
- 배열 접근시 경계 체크
- 정수형 타입의 변수에서 오버플로우 발생시 동작이 잘 정의되어 있음. 
    - Q. 오버플로우가 무슨말이지? float32같이 32 byte?(bit랑 또 헷갈린다. 개념이 구체적으로 뭐지?)를 넘어가는 숫자가 생기면 다시 -로 가던가 inf로 가는 현상을 의미하는게 맞아?
        - `<CLAUDE check>` bit와 byte: bit = 0 또는 1 한 자리, byte = 8 bit → float32는 32 bit = 4 byte
        - `<CLAUDE check>` 오버플로우(overflow): 계산 결과가 그 타입이 담을 수 있는 범위를 넘는 것, 방향은 맞는 이해
            - 예: 8 bit 부호 없는 정수는 0~255만 표현 가능, 255 + 1은 담을 수 없음
        - `<CLAUDE check>` 구분할 점: 이 항목은 정수 이야기, "inf로 가는 것"은 실수(float)의 동작이고 "반대쪽 끝으로 돌아가는 것"이 정수의 동작
        - `<CLAUDE check>` Python과 비교: Python의 `int`는 크기 제한이 없어 발생하지 않음, NumPy의 `int8` 같은 고정 크기 타입에서는 발생
        - `<CLAUDE check>` "잘 정의되어 있음"의 의미: 어떤 일이 일어날지 언어가 정해 둠
            - `cargo build`(디버그): 오류를 내고 프로그램 중단
            - `cargo build --release`: 반대쪽 끝으로 돌아감(255 + 1 → 0)
            - C에서는 일부 경우 무슨 일이 일어날지 정해져 있지 않음(정의되지 않은 동작)

최신 언어 기능: 상위 수준 언어만큼 표현력이 뛰어나고 인체공학적임
- 열거형과 패턴 매칭
    - Q. list, set, 정규표현식 같은걸 말하는 건가?
        - `<CLAUDE check>` 틀린 이해: list·set은 여러 값을 담는 컬렉션, 정규표현식은 문자열의 패턴을 찾는 도구로 이름만 비슷
        - `<CLAUDE check>` 열거형(enum): 가능한 경우를 몇 가지로 정해 둔 타입 (예: 신호등 = 빨강·노랑·초록 중 하나)
            - Python의 `enum.Enum`과 비슷, Rust에서는 각 경우가 데이터도 함께 가질 수 있음
        - `<CLAUDE check>` 패턴 매칭: 값이 어느 경우인지에 따라 갈라서 처리하고 안에 든 데이터를 꺼내는 문법 (`match`)
            - Python 3.10의 `match`-`case`와 비슷
            - 컴파일러가 모든 경우를 빠짐없이 다뤘는지 검사
- 제네릭
    - Q. 용어 정의 
        - `<CLAUDE check>` 제네릭(generic): 타입 자리를 빈칸으로 남겨 두고 작성하는 코드, 한 번 작성해서 여러 타입에 사용
            - 예: "무언가의 목록" `Vec<T>` 하나로 정수 목록 `Vec<i32>`, 문자열 목록 `Vec<String>`을 모두 표현
        - `<CLAUDE check>` Python과 비교: 원래 아무 타입이나 받으므로 필요를 못 느끼던 기능, 타입 힌트의 `list[int]`가 비슷한 표기
- FFI 런타임 오버헤드 없음
    - Q. 용어 정의
        - `<CLAUDE check>` FFI(Foreign Function Interface): 다른 언어(주로 C)로 작성된 함수를 호출하거나, 반대로 호출당하게 해 주는 통로
            - Python 예: NumPy가 내부에서 C 코드를 호출하는 것
        - `<CLAUDE check>` 오버헤드(overhead): 본래 하려는 일 외에 추가로 드는 시간·메모리
        - `<CLAUDE check>` "런타임 오버헤드 없음": Rust에서 C 함수를 부르는 비용이 일반 함수 호출과 같음, 중간 변환 단계 없음
- 비용이 들지 않는 추상화
    - Q. 추상화라는거는 뭔가 객체지향언어에서 들어본 class 부분인거 같은데, 이게 맞는지 맞다면 비용이 안든다는게 어떤 의미인지를 모르겠어. 
        - `<CLAUDE check>` 부분적으로 맞는 이해: class는 추상화의 한 가지 수단, 추상화는 더 넓은 개념
        - `<CLAUDE check>` 추상화(abstraction): 세부 동작을 감추고 편한 표현으로 쓰게 해 주는 것 (함수, class, 반복자, 제네릭 등)
        - `<CLAUDE check>` "비용이 들지 않는다": 편한 표현으로 써도 손으로 세세하게 짠 코드와 같은 속도의 기계어로 컴파일
            - Python과 비교: `for` 루프가 느려서 NumPy 연산으로 바꿔 쓰는 것이 "편한 표현에 비용이 붙는" 사례
- 친절한 컴파일러 오류메시지
- 내장 종속성 관리자, 테스트 지원
    - Q. 종속성 관리자, 테스트는 뭘 말하는 거지?
        - `<CLAUDE check>` 종속성(dependency): 내 프로그램이 가져다 쓰는 남의 라이브러리
        - `<CLAUDE check>` 종속성 관리자: 라이브러리를 내려받고 버전을 맞춰 주는 도구, Python의 `pip`·`conda`에 해당
            - Rust에서는 `cargo`가 담당 (`cargo add`로 추가, `Cargo.toml`에 목록 기록)
        - `<CLAUDE check>` 테스트: 코드가 기대한 대로 동작하는지 자동으로 확인하는 코드
            - Python은 `pytest` 등을 따로 설치, Rust는 `cargo test`로 바로 실행
        - `<CLAUDE check>` "내장": 따로 설치하지 않아도 `cargo` 하나에 모두 포함
- LSP(Language Server Protocal, 언어 서버 프로토콜) 지원이 잘되어 있음
    - Q. LSP가 구체적으로 뭔데? 또 위에서 말한 마이크로컨트롤러 위의 칩이랑은 또 다른건가? 
        - `<CLAUDE check>` 칩·하드웨어와는 무관, 코드 편집기에 관한 이야기
        - `<CLAUDE check>` LSP: 편집기(VS Code 등)와 언어 분석 프로그램(언어 서버)이 정보를 주고받는 통신 규칙
            - 제공 기능: 자동 완성, 오류 밑줄, 정의로 이동
            - Rust의 언어 서버: `rust-analyzer` (Python의 Pylance에 해당)
        - `<CLAUDE check>` 이름은 "서버"지만 인터넷 너머가 아니라 내 컴퓨터에서 편집기 옆에 함께 도는 프로그램
