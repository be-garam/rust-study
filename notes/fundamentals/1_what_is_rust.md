## Rust: 
- 2015년에 ver 1.0을 릴리즈한 새로운 프로그래밍 언어
    - [Rust blog: Announcing Rust 1.0](https://blog.rust-lang.org/2015/05/15/Rust-1.0/)
- 정적 컴파일 언어 (like C++)
    - Q. 정적 컴파일 언어가 뭐지? 이전에 이야기하던 바이너리를 만들어내는 언어? 
        - `<CLAUDE check>` 맞는 이해: 실행하기 전에 소스 코드 전체를 기계어(CPU가 직접 읽는 명령)로 미리 번역해 바이너리 파일을 만들어 두는 언어
        - `<CLAUDE check>` "정적" = "실행 전에(컴파일 시점에) 결정"이라는 뜻, 반대말 "동적" = "실행 중에 결정"
        - `<CLAUDE check>` 타입 검사도 실행 전에 끝남(정적 타입): 타입이 안 맞으면 바이너리 자체가 만들어지지 않음
        - `<CLAUDE check>` Python과의 차이: Python은 실행할 때 인터프리터가 소스를 읽어가며 처리, 타입 오류도 그 줄이 실행되는 순간에야 발견
    - 별도의 런타임을 필요로 하지 않고 가비지 컬렉션도 없음
        - Q. 런타임이 없다는건 os에서 프로그램을 실행시키는 시간인가? GC는 어떻게 없을 수 있지? 
            - `<CLAUDE check>` 런타임의 두 가지 뜻 중 다른 쪽: 여기서는 "실행 시간"이 아니라 "런타임 시스템"
                - 실행 시간(run time): 프로그램이 돌아가는 시점, 컴파일 시점의 반대말
                - 런타임 시스템(runtime): 내 프로그램이 돌아가려면 옆에서 함께 돌아야 하는 보조 프로그램 (예: Python 인터프리터, Java의 JVM)
            - `<CLAUDE check>` "별도의 런타임이 필요 없다" = 바이너리 하나만 있으면 실행 가능, Python처럼 상대 컴퓨터에 인터프리터를 설치할 필요 없음
                - 정확히는 `main` 시작 전 준비 작업 같은 아주 작은 런타임 코드가 바이너리 안에 포함됨, 인터프리터·가상 머신 같은 큰 런타임이 없다는 의미
            - `<CLAUDE check>` GC(가비지 컬렉션): 더 이상 쓰지 않는 메모리를 실행 중에 찾아서 자동으로 반납해 주는 런타임의 기능, Python이 이 방식
            - `<CLAUDE check>` Rust에 GC가 없어도 되는 이유: 메모리를 언제 반납할지를 컴파일러가 실행 전에 결정
                - 1. 모든 값에 주인(owner) 변수가 하나씩 정해짐
                - 2. 컴파일러가 주인 변수의 사용 범위(scope)가 끝나는 지점을 파악
                - 3. 그 지점에 메모리 반납 코드를 자동으로 삽입
                - 4. 실행 중에는 삽입된 코드가 그냥 실행될 뿐, 쓰레기를 찾아다니는 작업 없음
            - `<CLAUDE check>` 이 규칙이 소유권(ownership), Fundamentals 3일차 메모리 관리 단원에서 자세히 다룰 예정
- rustc: LLVM을 백엔드로 사용
    - Q. LLVM이 뭐지? 뭔가 웹개발에서의 백엔드랑은 개념이 다른거 같은데 
        - `<CLAUDE check>` 맞는 이해: 웹의 백엔드(서버)와는 다른 개념, "사용자와 맞닿지 않는 뒤쪽 절반"이라는 비유만 같음
        - `<CLAUDE check>` 컴파일러의 두 부분
            - 프론트엔드: 소스 코드를 읽고 문법·타입 등을 검사한 뒤 중간 표현(IR, 언어와 CPU 어느 쪽에도 묶이지 않은 중간 단계 코드)으로 변환
            - 백엔드: 중간 표현을 최적화하고 특정 CPU용 기계어로 변환
        - `<CLAUDE check>` LLVM: 이 백엔드 역할을 해 주는 오픈소스 컴파일러 도구 모음, C/C++(clang)·Swift 등도 함께 사용
        - `<CLAUDE check>` 컴파일 순서: Rust 소스 → (`rustc` 프론트엔드) → LLVM IR → (LLVM) → 최적화된 기계어 바이너리
        - `<CLAUDE check>` 장점: LLVM이 이미 지원하는 CPU 종류(x86, ARM 등)와 최적화 기술을 Rust가 그대로 활용 → 아래 "다양한 플랫폼과 아키텍쳐 지원"의 근거
- 다양한 플랫폼과 아키텍쳐를 지원하며 다양한 장치에서 사용될 수 있음 = C++가 사용되는 대부분의 곳에서 아용이 가능함
    - 높은 유연성과 제어, 마이크로컨트롤러 같은 제한된 장치로 스케일 다운이 가능
        - Q. 마이크로 컨트롤러가 뭐지? 뭔가 esp32라면 해당 부분에 들어간 칩? 이런걸 의미하는건가? 
            - `<CLAUDE check>` 맞는 이해: ESP32 칩이 바로 마이크로컨트롤러의 한 종류
                - 개발 보드 = 칩 + USB 단자·전원 회로 등 주변 부품, 마이크로컨트롤러는 그중 칩 자체
            - `<CLAUDE check>` 마이크로컨트롤러(MCU): CPU, 메모리(RAM), 저장 공간(플래시), 입출력 핀을 칩 하나에 모두 넣은 아주 작은 컴퓨터
                - 사용처: 세탁기, 리모컨, 센서, 키보드 같은 기기의 제어
            - `<CLAUDE check>` "제한된 장치"의 의미: RAM이 수 KB~수백 KB 수준(노트북은 수 GB, 대략 만 배 이상 차이), 운영체제 없이 프로그램 하나만 실행하는 경우가 많음
            - `<CLAUDE check>` 위 내용과의 연결: 런타임과 GC가 없어서 바이너리가 작고 운영체제 없이도 실행 가능 → 이런 작은 칩까지 스케일 다운 가능

## 토론: 마이크로컨트롤러에서 Rust가 돌아가는 방식
- Q. esp32 같은 마이크로컨트롤러에서는 무거운 python interpreter 대신 LLVM만 돌아가면 되니까 부하가 작은 건가? LLVM을 돌릴 수 있는 칩이라는 기준은 뭐지?
    - `<CLAUDE check>` 틀린 이해: LLVM은 칩 위에서 돌지 않음, 컴파일러의 일부라서 번역 작업을 하는 개발용 컴퓨터에서만 실행
    - `<CLAUDE check>` 실행까지의 순서
        - 1. 개발용 컴퓨터에서 `rustc`(+LLVM)가 Rust 소스를 칩의 CPU가 읽는 기계어로 번역
        - 2. 결과물인 바이너리를 USB로 칩의 저장 공간(플래시)에 옮김
        - 3. 칩에 전원이 들어오면 CPU가 그 기계어를 처음부터 하나씩 읽어 실행
        - 3번 시점의 칩 안에는 `rustc`도 LLVM도 없고 내 프로그램의 기계어만 존재
    - `<CLAUDE check>` 크로스 컴파일(cross-compile): 컴파일하는 컴퓨터와 실행하는 컴퓨터가 다른 방식
    - `<CLAUDE check>` "LLVM을 돌릴 수 있는 칩"이라는 기준은 없음, 올바른 기준은 "LLVM이 그 칩의 CPU용 기계어를 만들어 낼 줄 아는가"
    - `<CLAUDE check>` Python과의 차이
        - Python: 번역을 실행 중에 하므로 인터프리터가 칩 안에 함께 들어가 계속 돌아야 함, 인터프리터만 수 MB라 RAM이 수 KB~수백 KB인 칩에는 넣기 어려움
        - Rust: 번역이 끝난 기계어만 칩에 들어가고 실행 중에는 기계어 실행뿐
        - "무거운 인터프리터가 필요 없어서 부하가 작다"는 맞는 방향, 그 자리를 LLVM이 대신하는 것이 아니라 아무것도 대신하지 않음
- Q. 아니면 메모리쪽 사용량이나 계획이 미리 정해져서 그런가?
    - `<CLAUDE check>` 부분적으로 맞는 이해
        - 맞는 부분: 메모리를 언제 반납할지가 컴파일할 때 정해져서 실행 중에 GC가 돌 필요 없음, GC 코드와 GC가 쓰는 여유 메모리가 통째로 빠짐
        - 정확하지 않은 부분: 메모리를 얼마나 쓸지까지 전부 미리 정해지는 것은 아님, Rust 프로그램도 실행 중에 메모리를 더 요청할 수 있음 (스택/힙을 배울 때 다룰 내용)
- Q. rustc/LLVM은 vsc의 platformIO가 깔려있는 mac, window, ubuntu 같은 데에서 돌아간다고 이해하면 되나? 만들어서 칩에 옮기는 작업을 하는 게 arduino interpreter나 extension인 거고?
    - `<CLAUDE check>` 맞는 이해: `rustc`/LLVM은 개발용 컴퓨터에서 실행, 칩에 옮기는 일은 PlatformIO 같은 도구가 담당
    - `<CLAUDE check>` 고칠 용어: "Arduino 인터프리터"는 없음, Arduino 코드는 C++이고 Rust처럼 미리 컴파일되는 언어
    - `<CLAUDE check>` PlatformIO·Arduino IDE의 역할: 직접 번역하지 않고 다른 프로그램을 순서대로 불러 주는 관리자
        - 1. 컴파일러를 불러 소스를 칩용 바이너리로 번역
        - 2. 업로드 도구를 불러 바이너리를 USB로 칩의 플래시에 기록
    - `<CLAUDE check>` Rust에서는 `cargo`가 관리자 역할: `cargo`가 `rustc`를 불러 컴파일, 칩에 쓰는 일은 별도의 업로드 도구가 담당
- Q. esp32의 CPU는 전자두뇌 정도로 이해하고 있었는데, 해당 CPU의 규칙으로 바꾸는 작업이라는 개념도 들어가는 건가?
    - `<CLAUDE check>` 맞는 이해: CPU는 정해진 목록의 명령만 알아듣고, 그 목록이 CPU 계열마다 다름
    - `<CLAUDE check>` 아키텍처(architecture): 이 명령 목록의 종류
        - x86-64: Intel/AMD 노트북, 데스크톱
        - ARM: 스마트폰, Apple Silicon Mac, 많은 마이크로컨트롤러
        - Xtensa, RISC-V: ESP32 계열
    - `<CLAUDE check>` 같은 "두 수를 더해라"도 아키텍처마다 다른 숫자 조합으로 표기 → 노트북용 바이너리를 ESP32에 넣으면 실행 불가
- Q. rustc로 만들어둔 파일이 binary로 전환되는 과정은 LLVM이 하는데, 칩의 특성에 따라 작성되는 binary는 다를 수 있다는 정도로 이해해도 되나?
    - `<CLAUDE check>` 맞는 이해, 다만 "다를 수 있다"가 아니라 아키텍처가 다르면 반드시 다름
    - `<CLAUDE check>` LLVM은 `rustc` 안에 포함: 따로 실행하지 않고 명령 한 번에 소스에서 바이너리까지 진행
    - `<CLAUDE check>` 중간 결과물(IR)은 그 과정 안에서 넘겨지는 것이라 보통 파일로 보이지 않음
    - `<CLAUDE check>` 타깃(target): 어떤 칩용으로 만들지 컴파일할 때 지정하는 값, 같은 소스라도 타깃을 바꾸면 다른 바이너리 생성
